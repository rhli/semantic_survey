# 上下文层的四条路线

## 结论先行

所有厂商都承认同一个问题：**人工建模的语义层覆盖不了企业的长尾语义**。指标口径、业务规则、表的真实用途大量散落在 dashboard、查询、wiki、Slack、工单里，从未被显式定义过。AI agent 找不到就会猜。

分歧不在问题诊断，而在**上下文应该存在哪里、谁拥有它、以及冲突时如何仲裁**。目前有四条互不兼容的答案：

| 路线 | 代表 | 上下文存在哪 | 从哪来 | 冲突仲裁 | 消费方式 | 谁拥有 |
|---|---|---|---|---|---|---|
| **自动图谱 + 权威度排序** | [[Genie Ontology]] | 平台内的活图谱 | 自动抽取（表/查询/dashboard/管道 + 50+ 外部工具） | **OntoRank**（PageRank 式加权） | 平台内 + MCP | 厂商 |
| **自动生成 + 人工确认** | [[Snowflake Semantic Views]] Autopilot | 平台 catalog 内的语义视图 | 从 BI 使用模式自动生成，交人审核 | 不需要——终点是单一人工确认定义 | 平台内 | 厂商 |
| **跨平台摄取 + 治理绑定** | [[Atlan]] Enterprise Data Graph | 外部 SaaS 的 graph | 摄取他家语义定义（dbt/Cube/LookML/UC Metrics）+ 绑定治理元数据 | 未见公开机制 | MCP | 厂商 |
| **发布进客户数仓的 SQL 表** | [[Agents Schema]] | **客户自己数仓的 `AGENTS` schema** | 从原本拥有元数据的系统发布（CI/CD、workflow） | **不做**——只做发现层 | **裸 SQL**（MCP 可选） | **客户** |

前三条共同假设"上下文是一个服务"，第四条主张"上下文是数据"。这是这张表里最大的一道分界线。

## 逐条分析

### 1. 自动图谱 + 权威度排序（Databricks）

**核心押注**：接受"企业大部分语义永远不会被显式建模"这一现实，转而用排序机制在混乱中找出最可信的那一条。

它是唯一直面**冲突仲裁**问题的方案。同一个概念在 Slack 里、在某张 dashboard 里、在某个认证 Metric View 里各有一个定义时，OntoRank 按来源类型、作者权威度、被依赖频率、与认证资产的关联紧密度、新鲜度加权，让人工治理的定义**自动获得优先级**而不需要显式路由规则。

它与人工定义的关系是**并存互补**，不是替代——认证的 Metric View 是校准排序的高权威度锚点。详见 [[2026-07-31 Databricks 的双层语义架构]]。

**软肋**：只能映射已经存在于某处的含义，基础数据薄弱时会忠实地把乱麻映射出来。OntoRank 的可解释性与可干预性未公开。状态为 gated public preview。

### 2. 自动生成 + 人工确认（Snowflake）

**核心押注**：自动化用在**降低建模成本**上，而非扩大覆盖面。Autopilot 分析 BI 工具中指标当前的计算方式（Looker、dbt、Sigma、ThoughtSpot），提议语义视图定义，人审核确认。

这是四条中最保守也最可控的一条：**最终事实源仍然唯一**，不引入概率性的第二层，因此不需要仲裁机制。代价是覆盖面天花板等于人愿意审核的量。

**待深研**（Snowflake 尚未深研，本节结论置信度较低）：Autopilot 生成质量、审核工作量、以及 Snowflake 是否会跟进类似 Ontology 的自动上下文层。后者是判断"双层语义是否为可推广范式"的关键信号。

### 3. 跨平台摄取 + 治理绑定（Atlan）

**核心押注**：语义定义已经存在于各家平台里，缺的是**跨平台的统一上下文与治理绑定**。因此不自产定义，而是摄取并在自己的 graph 中重新表达，加上治理元数据（所有者、认证状态、质量、血缘），经 MCP 交付。

它是唯一真正跨数据平台的方案——其他三条都或多或少绑定在单一平台或单一数仓上。这也是它与 Genie Ontology 互称"互补"的基础（Atlan 向 Genie 反馈跨系统上下文）。

**待深研**（Atlan 尚未深研）：与 Genie Ontology 的真实重叠度、冲突仲裁机制、以及"多一跳外部 SaaS"在延迟与可用性上的代价。

### 4. 发布进客户数仓的 SQL 表（Agents Schema）

**核心押注**：上下文不该是新的基础设施或服务，而应该是**客户数仓里的普通表**。存 `AGENTS` schema，任何能跑 SQL 的 agent 都能读，MCP 只是可选项之一。官方类比是"数据仓库的 `AGENTS.md`"。

这条路线在**避免锁定**这个维度上最强，也是唯一把上下文所有权明确交给客户的方案。几处设计取向值得注意：

- 为 LLM 消费者**放弃强 schema**：`AGENTS.ROOT` 只有 `(provider, key, content)` 三列，content 是允许改变形状的自由文本。承认下游是能读自然语言的模型。
- 把 **OSI 定为 canonical 语义格式**，而非自家 MetricFlow YAML。开放叙事的实质动作。
- 对原生语义层克制：Snowflake Semantic 只写指针行，不镜像定义。
- 顺带成为 **prompt/指令的分发通道**（skills 机制）。

**两处硬伤**：

1. **权限模型远弱于其他三条**。规范要求 `AGENTS.*` 对任何运行分析或 agentic 查询的仓库主体可读。数据本身不动，但业务逻辑、指标口径、血缘、所有者、运营指令对全体查询者可读。Genie Ontology 与 Atlan 都做逐来源 ACL 执行。
2. **不做仲裁、不保证正确性**。它只是发现层——告诉 agent 定义是什么，agent 拿到后仍是自由写 SQL。这是它与语义层的分工，也是它的天花板。

## 关键区分维度

把四条路线拉开的其实是三个正交问题，值得分别追踪：

**（1）覆盖面 vs 可信度如何取舍**

Databricks 选"广覆盖 + 概率可信度 + 排序仲裁"，Snowflake 选"窄覆盖 + 确定可信度"。这是同一个 trade-off 的两端。Atlan 与 Agents Schema 则回避了这个取舍——它们只搬运已有定义，不生产新的语义，所以覆盖面等于上游各家之和，可信度继承上游。

**（2）上下文的新鲜度语义**

| 路线 | 更新机制 |
|---|---|
| Genie Ontology | 每次有东西变化就自动重建（活图谱） |
| Snowflake Autopilot | 人工审核周期 |
| Atlan | 连接器同步周期 |
| Agents Schema | 外部 CI/CD 触发，`CREATE OR REPLACE TABLE` 整表替换 |

后两条是批量快照语义，与"活图谱"有本质差别。上下文过时导致 agent 用旧口径作答，是这个赛道尚未被认真讨论的失效模式。

**（3）元数据本身是否需要访问控制**

这是 Agents Schema 暴露出的新问题，而且它不只是 Agents Schema 的问题——一旦上下文层要服务 agent，"谁能看到指标是怎么算的"就与"谁能看到数据"分离了。Genie Ontology 与 Atlan 选择让二者一致（逐来源 ACL），Agents Schema 选择让元数据全员可读。哪一种是对的取决于场景：指标口径本身敏感（未公开财务口径、定价逻辑）时，前者必需。

## 一个共同的空白

四条路线都解决"上下文如何被表示、发现、分发"，**都不解决"上下文如何被验证并保持正确"**。

- Genie Ontology 的 OntoRank 排序权威度，但权威 ≠ 正确，且薄弱的基础数据会被忠实映射。
- Snowflake 的人工审核是一次性的，审核过的定义不会自动跟随业务变化。
- Atlan 的治理元数据（认证状态）是人工维护的标记，不是持续验证。
- Agents Schema 明确只做发现层，不做任何正确性保证。

一个完美可发现、完美可分发、但六个月前写好再没人碰过的指标定义，仍然是过时的。这是下一层工具的机会空间（Datus 持此观点，虽服务其商业定位但判断成立）。

## 置信度

| 判断 | 置信度 | 说明 |
|---|---|---|
| 四条路线的机制描述 | Databricks、Agents Schema **高**；Snowflake、Atlan **低** | 前两家有官方规范级材料 + 第三方交叉；后两家仅凭二手 landscape 材料，尚未深研 |
| "上下文是服务 vs 上下文是数据"是主分界线 | **中高** | 从四家的架构选择归纳，逻辑一致，但 Snowflake/Atlan 侧证据薄 |
| 元数据访问控制会成为真实议题 | **中** | 从 Agents Schema 规范与其他家的 ACL 设计对比推出，未见任何厂商或客户公开讨论 |
| "四条路线都不解决保持正确"这一空白 | **中高** | 四家材料中均未见相关机制，但缺席证据弱于正面证据 |
