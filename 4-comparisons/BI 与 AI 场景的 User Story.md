# BI 与 AI 场景的 User Story 对比

## 结论先行

同一个业务问题，在 BI 和 AI 两种场景里走的是完全不同的故事线，而**语义层在两条故事线里扮演的角色根本不同**：

- **BI 场景**：语义层是分析师的**效率工具**——少写重复 SQL、口径统一。没有它，故事照样走完，只是慢和乱。
- **AI 场景**：语义层是 agent 的**安全网**——没有它，故事直接走向静默错误，而且没有任何角色负责发现问题。

一句话：**BI 时代语义层兜的是"效率"，AI 时代兜的是"正确性"**。这个转变决定了语义层从 nice-to-have 变成 must-have，也解释了 2024 年后这个市场的爆发。

## 场景设定

一家电商公司，数仓里有 `orders`（订单事实表，一行一个订单明细）、`customers`（客户维度表）、`refunds`（退款表）。业务方是运营总监，数据团队维护着一套语义层。

贯穿全文的同一个问题：**"上个月各品类的 GMV 怎么样？"**

## BI 场景的故事线

### 故事 1：分析师做看板（语义层在场）

> 运营总监在周会上问："上个月各品类 GMV 怎么样？"
>
> 分析师小王打开 BI 工具，拖拽：维度选"品类"，指标选"GMV"，时间过滤选"上月"。GMV 的口径（是否含退款、是否含税）在语义层里已经定义好，小王不用关心。看板下午就挂出来了。

语义层的角色：**省时间**。小王不用写 SQL，不用回忆 GMV 到底减不减退款。

### 故事 2：分析师做看板（语义层缺席）

> 同样的提问。小王写 SQL：`SELECT category, SUM(amount) FROM orders JOIN ...`。他记得 GMV 要扣退款，于是 left join 了 `refunds` 表再相减。
>
> 但他不知道 `refunds` 一行订单可以有多条退款记录——join 之后订单行被复制，`SUM(amount)` 把同一笔订单金额算了两遍。看板上的 GMV 比实际高了 8%。
>
> 数字看起来"很合理"。直到月底财务对账时发现对不上，往回追了三天才定位到这个 fan-out 错误。

语义层缺席时的兜底者是**人**——财务对账、分析师的直觉、跨部门扯皮。错误会被发现，只是代价大、周期长。这就是 [[Join 正确性的保证方式]] 里 fan-out 的经典剧本。

### 故事 3：口径变更

> 公司决定 GMV 口径从"下单时间"改为"支付时间"。
>
> 有语义层：数据团队改一处定义，全部看板自动生效，半天收工。
> 没语义层：小王逐个排查 47 张看板里手写的 SQL，改了两周，漏了 3 张，三个月后还有人在用过期口径做汇报。

语义层的角色：**一致性**。这是 BI 时代语义层最古老的价值主张（"三个系统三个 revenue"的解药）。

## AI 场景的故事线

现在公司上线了 ChatBI（[[Text2SQL]]），运营总监直接问 agent，不再经过分析师。

### 故事 4：业务直接提问（语义层在场）

> 运营总监在对话框输入："上个月各品类的 GMV 怎么样？"
>
> Agent 把问题解析为对语义对象的引用：指标 `gmv`、维度 `category`、时间 `last_month`。[[Semantic Layer]] 引擎确定性编译成 SQL——GMV 的口径、join 路径、退款扣除逻辑全部来自治理过的定义。
>
> 3 秒后返回答案，附带一句："GMV 口径为支付成功且扣除退款，统计区间为 2026-07-01 至 07-31。"

语义层的角色：**grounding**。LLM 不碰物理表，只在受约束的语义空间里操作，join 正确性由引擎保证。这是 [[Text2SQL]] 页里"声明式定义 + 查询时编译"路线（[[Genie]]、[[Cortex Analyst]]）的标准流程。

### 故事 5：业务直接提问（语义层缺席）

> 同样的提问。Agent 直接对裸 schema 生成 SQL。
>
> 它猜 `gmv` 就是 `SUM(amount)`——没扣退款；它把 `orders` 和 `refunds` join 在一起——触发了和故事 2 一模一样的 fan-out；它还自作主张按"下单时间"过滤，而公司口径是支付时间。
>
> SQL 跑通了，数字返回了，**看起来完全合理**。运营总监拿着错数去开了经营分析会。

这是 AI 场景最危险的地方：**错误静默，且没有任何角色负责发现**。BI 时代有分析师的专业直觉和财务对账兜底；AI 场景里提问的是业务方，他没有能力也没有预期去验证 SQL。准确率数据（裸 schema 6–40%，grounding 后 90%+）背后是故事 4 和故事 5 的分野。

### 故事 6：长尾问题

> 运营总监追问："那新客贡献的 GMV 占比呢？就是我们 618 活动拉来的那批。"
>
> "新客"和"618 活动拉来"这两个概念从未被显式定义过——它们存在于某张活动复盘看板里、某个分析师的 SQL 里、某条 Slack 讨论里。
>
> 语义层只覆盖了常规指标，接不住这个问题。Agent 要么猜（回到故事 5 的风险），要么说"我不知道"（体验差）。

这是 [[上下文层的四条路线]] 共同面对的**长尾语义**问题。两条出路：

- **从使用痕迹里挖**：[[Snowflake Semantic Views]] Autopilot 从 BI 使用模式（查询日志、Looker/Sigma 模型）自动提议定义，交人审核；[[Genie Ontology]] 更激进，从 dashboard、Slack、工单等 50+ 来源建活图谱，用 OntoRank 排权威度。
- **消歧与澄清**：agent 反问"你说的新客是指首次下单用户吗？"——把 BI 时代分析师的"确认需求"环节搬进对话。

### 故事 7：口径变更（AI 版）

> 公司决定 GMV 口径改为支付时间。
>
> 有语义层：改一处定义，agent 的所有回答即时生效——和故事 3 一样。
> 没语义层：**没有东西可改**。口径散落在 agent 每次即兴生成的 SQL 里，今天和明天的回答可能都不一样，且无人察觉。

AI 场景把"口径一致性"从治理诉求变成了**正确性诉求**：BI 时代口径不一致是"三个部门三个数、开会吵架"；AI 时代是"同一个 agent、同一个问题、两个答案"。

## 对照矩阵

| 维度 | BI 场景 | AI 场景 |
|---|---|---|
| 消费者 | 分析师（懂数据、有怀疑能力） | 业务方 / agent（无验证能力） |
| 提问方式 | 拖拽、点选、预定报表 | 自然语言、开放域、组合爆炸 |
| 语义层缺席时 | 慢、乱、口径打架，但**人会兜底** | 静默错误，**无人兜底** |
| 语义层的角色 | 效率工具 + 一致性工具 | 正确性前提（grounding） |
| 错误的可见性 | 数字离谱会被看出来 | SQL 跑通即"成功"，错得不动声色 |
| 覆盖要求 | 覆盖核心指标即可 | 必须面对长尾（自动化生成 / 消歧） |
| 口径变更 | 改一堆看板 vs 改一处定义 | 改一处定义 vs 无处可改 |

## 对语义层设计的含义

1. **正确性机制的优先级反转**。BI 时代 fan-out 防护是加分项（分析师会复核）；AI 时代是必需品，因为消费结果的人/系统没有复核能力。这直接抬高了 [[Join 正确性的保证方式]] 这个维度的权重。
2. **"拒绝回答"成为功能**。BI 工具不需要"拒绝出数"的能力；agent 必须在语义覆盖不了时能消歧、能澄清、能承认不知道，而不是硬猜。
3. **语义来源必须自动化**。BI 时代人工建模覆盖核心指标就够；AI 场景的长尾问题逼着厂商从 BI 使用模式和组织产出里自动挖语义（Autopilot、Genie Ontology），人工治理退为审核与高权威锚点。
4. **口径说明要随答案返回**。故事 4 里那句"GMV 口径为……"不是客套，是 AI 场景替代分析师背书的方式——答案必须自带可审计性。
