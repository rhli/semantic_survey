# Aloudata CAN

## 定位与解决的问题

NoETL 自动化指标平台。针对传统指标平台"先建宽表再定义指标"的模式（开发周期长、灵活性差、表资产爆炸），主张**明细级语义层**：配置化定义指标，免宽表，任意粒度/维度动态下钻，性能靠自动物化兜底。口号："定义即治理、定义即开发、定义即消费、定义即沉淀"。

## 核心概念与架构

- **虚拟全域明细宽表**：在逻辑层把 DWD 明细表与维表关联成一张虚拟宽表，覆盖所有业务事实与维度——物理层不打宽，语义层"逻辑打宽"。
- **要素化声明定义**：表被抽象为度量/维度/限定三类要素，界面点选即可定义任意业务逻辑指标（如"销售额 = SUM(订单事实.金额)"），系统自动解析语义、生成可执行逻辑计划与无歧义 SQL。
- **三级智能物化**：明细/汇总/预计算三级物化策略，由智能引擎按查询模式与数据分布动态决策；查询时自动改写 SQL 精准命中已物化结果。宣称亿级数据秒级响应。
- **ETL 代持**：物化任务的生成、调度、依赖管理、监控告警全部平台自动完成——这是 "NoETL" 的实际含义：不是没有 ETL，而是 **ETL 从人工编排变成平台代持的物化运维**。
- 指标治理：定义时自动"同名不同义、同义不同名"判重；字段级指标血缘；指标多版本。
- 开放服务：API/JDBC，支撑仪表板、自助分析、归因、监控预警；上游出口是 Aloudata Agent（NL2MQL2SQL）。

## 语义模型的表达方式

配置化定义（指标要素：度量/维度/限定），无独立 DSL 文件——与 metrics-as-code 阵营（MetricFlow YAML、Cube JS/YAML、SML）形态不同，模型活在平台内而非 Git 仓。这是国内指标平台与国际 metrics-as-code 阵营的形态分野：**治理在平台 UI 里，版本化与代码审查能力待核实**。

## 限制与边界

- 跨源联邦能力依赖 Aloudata AIR 组合部署（CAN 本身建在数仓 DWD 层之上）。
- 超大规模场景的物化成本曲线待验证——"智能物化"的经济性取决于命中率，冷查询仍落回明细扫描。
- 平台内建模的形态对"模型即代码"实践（diff review、CI）的支持程度未知。
